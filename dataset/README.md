# Dataset

Эта папка хранит исходные рукописные траектории, текстовые подписи к ним и
сгенерированный `.npz`-датасет для обучения модели.

## Структура

```text
dataset/
  jsons/                  Исходные траектории: trajectory_<id>.json
  texts/                  Подписи: trajectory_<id>.txt
  scripts/                Утилиты для сбора, просмотра и разметки датасета
  npzs/                   Промежуточные .npz-файлы, генерируются автоматически
  all_trajectories.npz    Итоговый датасет для src/dataset.py
  target_texts.txt        Слова для режима candidate generation
  trash/                  Старые/ручные тестовые файлы
```

`jsons/` и `texts/` - это источник данных. `npzs/` и
`all_trajectories.npz` - build artifacts: их можно пересобрать.

Важное правило кодирования: `\n` в подписи считается обычным переносом строки,
а конец обучающего фрагмента добавляется конвертером отдельным токеном `<EOS>`.
Это нужно, чтобы модель не путала перенос строки с концом текста.

Кавычки подготовлены под русский рукописный стиль:

- `„` - будущая нижняя открывающая кавычка;
- `“` - верхняя кавычка.

Старые прямые кавычки были заменены на `“`, чтобы в алфавите не было двух
разных верхних кавычек. Когда появятся новые траектории с нижней открывающей
кавычкой, их подписи лучше записывать как `„текст“`.

## Формат trajectory JSON

Каждый `dataset/jsons/trajectory_<id>.json` содержит список точек:

```json
[
  [x, y, state],
  [x, y, state]
]
```

Где:

- `x`, `y` - координаты пера/курсора.
- `state = 0` - перо продолжает текущий штрих.
- `state = 1` - конец штриха / pen-up.

Файл `dataset/texts/trajectory_<id>.txt` должен содержать текст, который
написан в соответствующей траектории.

## Сборка датасета

Основной способ из корня проекта:

```bash
.venv/bin/python scripts/handwriting.py dataset
```

Прямой запуск конвертера:

```bash
.venv/bin/python dataset/scripts/converter.py
```

Конвертер:

1. Читает пары `jsons/trajectory_<id>.json` и `texts/trajectory_<id>.txt`.
2. Нормализует переносы строк и убирает один финальный `\n`, если он попал в
   TXT как технический конец файла.
3. Кодирует текст в индексы символов из `src/config.py`.
4. Добавляет отдельный `<EOS>`-токен в конец каждой подписи.
5. Пишет промежуточные файлы в `dataset/npzs/`.
6. Собирает общий `dataset/all_trajectories.npz`.

## Скрипты

```text
dataset/scripts/converter.py
```

Собирает `all_trajectories.npz` из `jsons/` и `texts/`. Это основной скрипт,
который нужен перед обучением после изменения исходных данных.

```text
dataset/scripts/label_trajectories.py
```

Tkinter/Matplotlib-интерфейс для просмотра траекторий и создания/правки
подписей в `dataset/texts/`. По умолчанию открывается в режиме просмотра.

```bash
.venv/bin/python dataset/scripts/label_trajectories.py --review
.venv/bin/python dataset/scripts/label_trajectories.py --edit
.venv/bin/python dataset/scripts/label_trajectories.py --start 120 --edit
```

```text
dataset/scripts/handrwritting.py
```

Старый Tkinter-редактор для записи траектории мышью/пером. Сейчас сохраняет
только JSON в `dataset/jsons/`, без текстовой подписи. После него нужно вручную
создать соответствующий `dataset/texts/trajectory_<id>.txt` или открыть
`label_trajectories.py --edit` и подписать новый образец там.

```text
dataset/scripts/compare_line_spacing.py
```

Сравнивает вертикальный масштаб нового многострочного образца с текущим
датасетом. Это полезно при записи на новом устройстве: скрипт показывает
центры строк, расстояние между ними, высоту букв и варианты `gridStepMm` для
текущего `ydpi`.

```bash
.venv/bin/python scripts/handwriting.py compare-spacing \
  --sample path/to/trajectory_1.json
```

## Добавление новых образцов

1. Создать `dataset/jsons/trajectory_<new_id>.json`.
2. Создать `dataset/texts/trajectory_<new_id>.txt` с точной подписью вручную
   или через:

```bash
.venv/bin/python dataset/scripts/label_trajectories.py --start <new_id> --edit
```

3. Пересобрать датасет:

```bash
.venv/bin/python scripts/handwriting.py dataset
```

4. Проверить состояние проекта:

```bash
.venv/bin/python scripts/handwriting.py status
```

## Разделение на однострочные примеры

`scripts/split_lines.py` находит возвраты пера на следующую физическую строку.
Он работает на стандартной библиотеке Python 3.10+, без PyTorch и NumPy.
Команды ниже запускаются из корня проекта любым рабочим Python.

Сначала получить отчёт с цветным просмотром траекторий, без экспорта пар:

```bash
python dataset/scripts/split_lines.py --output-dir runs/line_split/preview_new
```

В выходной папке появятся `index.html` и `report.json`. Нужна новая или пустая
папка: существующие результаты скрипт не перезаписывает.

Экспортировать однострочные JSON/TXT в отдельный набор:

```bash
python dataset/scripts/split_lines.py --write --output-dir dataset/single_line --overrides dataset/line_split_overrides.json
```

Результат:

```text
single_line/
  jsons/trajectory_1.json
  texts/trajectory_1.txt
  ...
  manifest.json
  report.json
  index.html
```

Скрипт проверяет одновременно:

- предыдущая точка имеет `state=1` — перо поднято после завершения штриха;
- `dx` направлен влево, минимум на 35% ширины исходной записи;
- `dy` направлен вниз минимум на типичную высоту ближайших штрихов;
- медиана y в следующих точках устойчиво ниже, чем перед скачком.

Высота оценивается по восьми ближайшим подходящим штрихам; окно устойчивого
сдвига — до 150 точек с каждой стороны. Короткий остаток строки допустим.
Пороги доступны как `--min-return-fraction`, `--min-down-factor`,
`--context-points`. Это эвристика для текущих экранных координат (y растёт
вниз), а не универсальный детектор любой разметки листа.

Все найденные границы учитываются, поэтому поддерживаются и три строки.
Разрез проходит **перед первой точкой новой строки**, не внутри штриха.
Координаты, их порядок, конечные точки и состояния пера сохраняются точно;
масштабирование, усечение по длине и пересэмплирование здесь не выполняются.
При двух строках получается два файла JSON и две точные TXT-подписи.
Однострочные исходники тоже включаются в новый набор.

TXT разделяется по настоящим `\n`. Число подписей должно совпасть с числом
геометрических строк. Слабые кандидаты, неверные данные, несоответствие подписей
и возможные отложенные штрихи попадают в `needs_review` и не экспортируются.
Программа не угадывает, какое слово написано на каждой стороне разреза.
Дефисы сохраняются: `бу-\nлок` превращается в `бу-` и `лок`, вместе с
соответствующим рисунком. Отрыв пера внутри слова не считается его границей.

`line_split_overrides.json` содержит отдельно проверенные границы и подписи
для исходников 171, 222 и 235: в их TXT отсутствовал физический перенос.
У 222 на рисунке также есть дефис в `открыл-` / `ся.`, которого не было в TXT.
Исправления применяются только к экспорту; исходные подписи не меняются.
Формат ручного уточнения:

```json
{"trajectory_171": {"breaks": [1709], "texts": ["Текст первой строки", "Текст второй строки"]}}
```

Индексы `breaks` отсчитываются от нуля и указывают первую точку следующей
строки. Неверный индекс или разрез внутри штриха отклоняется. После изменения
исходных записей ручные уточнения необходимо перепроверить.

Выходные ID — новые последовательные числа, совместимые с конвертером.
`manifest.json` связывает их с `source_id`, номером строки, исходным диапазоном
точек `[start, stop)`, SHA-256 источников и признаком переноса слова.
**Все строки одного `split_group` должны попадать в одну часть train/val/test.**
Текущий случайный split в обучении этого пока не учитывает; автоматически
подключать новый набор к обучению скрипт не будет. Лимит 3000 точек в загрузчике
тоже надо исправлять отдельно: длинная однострочная запись остаётся длинной.

На наборе из 472 исходников: 169 геометрических переходов, 635 готовых строк
без уточнений и 641 строка с тремя проверенными уточнениями.

Проверки сохранности и поведения CLI:

```bash
python -m unittest discover -s tests -p test_split_lines.py -v
```

## Аудит датасета

После пополнения или правки подписей полезно проверить покрытие символов и
длины примеров:

```bash
.venv/bin/python scripts/handwriting.py audit-dataset
```

Команда создаёт Markdown-отчёт:

```text
runs/dataset_audit.md
```

В отчёте видно:

- сколько примеров есть в `jsons/` и `texts/`;
- какие символы реально встречаются в подписях;
- какие символы из `CHAR_SET` не используются;
- какие символы встречаются слишком редко;
- сколько `<EOS>`-токенов попало в собранный `.npz`;
- сколько есть пробелов, пунктуации, цифр и заглавных букв;
- распределение длин текста и траекторий;
- какие примеры будут обрезаны при текущем `max_seq_len`.

## Целевые слова

`dataset/target_texts.txt` не участвует в обучении напрямую. Это список слов или
коротких фраз для генерации и ранжирования кандидатов:

```bash
.venv/bin/python scripts/handwriting.py candidates \
  --texts dataset/target_texts.txt \
  --output-dir runs/candidates/run_01
```

## Что хранить в Git

Обычно стоит хранить:

- `dataset/jsons/`
- `dataset/texts/`
- `dataset/scripts/`
- `dataset/README.md`
- `dataset/target_texts.txt`

Обычно не стоит хранить:

- `dataset/npzs/`
- `dataset/all_trajectories.npz`
- временные файлы из `dataset/trash/`
